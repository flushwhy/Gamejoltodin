# Contributing

## Commit messages

This repository uses [Conventional Commits](https://www.conventionalcommits.org/) so release-please can calculate versions and generate changelog entries.

Use this format:

```text
<type>[optional scope][!]: <summary>
```

Examples:

- `feat: add trophy helpers` — a backward-compatible feature; normally a minor release.
- `fix: handle empty score tables` — a backward-compatible bug fix; normally a patch release.
- `docs: clarify C ABI usage` — documentation-only change.
- `test: cover URL signing` — tests.
- `ci: repair Windows build setup` — CI/workflow changes.
- `refactor: simplify session state` — internal change.
- `feat!: redesign session initialization` — breaking change; normally a major release.

For a breaking change without `!` in the header, include a footer such as:

```text
BREAKING CHANGE: explain what callers must change.
```

Use imperative, concise summaries. Avoid custom release prefixes such as `version-`, `release-`, or manually numbered commit titles.

## Releases

Releases are managed by release-please using the root `release-please-config.json`.

- The release PR title and changelog are generated by release-please; do not hand-create or rename release PRs to a custom format.
- Release tags use the standard `vX.Y.Z` format.
- Merge the release PR to publish the GitHub Release. The release workflow then builds and attaches platform archives.
- Keep commits on the default `master` branch in Conventional Commit format so release-please can determine the correct next version.
